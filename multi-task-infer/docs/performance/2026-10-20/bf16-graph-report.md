# BF16：eager 与 Ascend decode 图模式对比

2026-10-20；Qwen3.5-9B，16 张 Ascend910，8×TP=2，共用同一批 16 个 Worker Actor。

两组显式设置权重与 Mamba 缓存 BF16；max_model_len=1024、max_num_seqs=4、
max_num_batched_tokens=2048、显存比例0.65、关闭 prefix cache、纯文本。
图组使用 VLLM_COMPILE + FULL_DECODE_ONLY，捕获 batch 1/2/4；prefill 不走 ACL 图。
因此这是后端支持的“编译+decode图”相对 eager 的整体收益，未单独隔离编译收益。

每组先预热，再对四种负载各测3批；固定生成64 token，temperature=0、ignore_eos。
共240个正式请求/组；profiler在正式测量之后独立运行。

## 正确性与资源释放

按负载批次与实例比较的 240 个贪心请求输出中，0 个 token 序列不同。这只是固定提示回归检查，不代表模型精度评测。

- eager：每卡图捕获内存 0–0 MiB；退出后16卡通信域、coordinator、图条目均清空，Actor PID全部保持不变。
- graph：每卡图捕获内存 274–300 MiB；退出后16卡通信域、coordinator、图条目均清空，Actor PID全部保持不变。

Actor保留设备上下文和框架常驻缓存，退出后显存不要求归零。图已实际回放，原始Actor日志包含 `Replaying aclgraph`。
正常退出仍可能输出 AsyncLLM output_handler 的 EngineDeadError 日志；本次请求均完成，资源释放断言通过，此日志竞态尚未修复。

## 编译缓存限制

首次完整图测试加载磁盘AOT缓存后失败：图内固化了已销毁的旧TP组名 `tp:11`。
正式图结果使用 `VLLM_DISABLE_COMPILE_CACHE=1`，禁止加载/保存此类持久化缓存；每个engine仍重新编译、捕获、回放。
测试脚本在空闲Actor内设置该开关，测试后恢复原环境；没有修复后端缓存键或重绑定通信组。
eager组不执行编译，因此此开关不影响eager基线。图捕获日志每实例约1–2秒、每卡300MiB。
CPU和权重页缓存已热；图组禁用了vLLM持久化编译缓存，不能将本结果视为首次整机冷启动。
启动增加约1.47秒是两组均值之差，不是通过独立计时隔离得到的纯编译时间。
失败原始记录保存在 failed-cache-metrics.json 和 failed-cache-run.log。

新建 EngineCore 和两个 TP Worker，BF16、VLLM_COMPILE + FULL_DECODE_ONLY、batch 1/2/4，其余配置与上表一致。

## 计时口径说明

直接启动包含 driver 导入为92.03秒；从创建引擎到ready为76.99秒。资源池已就绪时，接到配置后到ready平均16.53秒，范围15.68–18.73秒。因此可以说请求路径由约92秒缩短到约16–20秒，但两者起点不同：池化将导入和部分初始化提前完成，池预热成本没有消失。图测试的8个CPU Core预热另耗18.74秒，Worker Actor池此前已建立；首次部署总耗时不能直接按16–20秒计算。同口径创建引擎到ready的比较为76.99秒对16.53秒。

## 16.53秒启动拆解

基于本轮8个TP=2实例的日志逐一对齐，平均16.527秒，范围15.677–18.728秒。Actor与CPU EngineCore预热池已就绪；每次重新加载模型并初始化通信域，禁用vLLM持久化编译缓存。

| 阶段 | 平均耗时 | 占总时间 | 计时边界与含义 |
| --- | ---: | ---: | --- |
| 前端初始化与Core激活 | 3.73秒 | 22.6% | 创建配置/AsyncLLM开始，到Core打印初始化日志；包含配置准备、客户端建立、发送配置和进程激活，尚无内部独立计时 |
| Worker/executor初始化与模型加载 | 4.39秒 | 26.5% | Core初始化日志，到profile/KV/warmup阶段起点；包含Worker初始化、通信域建立、模型加载及RPC等待 |
| 内存profile、KV初始化、编译与warmup | 6.61秒 | 40.0% | Core明确记录的阶段总时长，范围6.17–7.73秒；包含图捕获 |
| ready收尾 | 1.80秒 | 10.9% | 上阶段结束，到AsyncLLM构造返回；包含Core剩余初始化、ready握手和客户端返回 |
| 合计 | 16.53秒 | 100% | 8实例均值 |

主阶段可相加；下列细项已包含在主阶段中，不能再加到16.53秒上：

- 模型加载：两TP rank取较慢者，再对8实例求均值，为3.72秒（3.49–4.33秒），位于4.39秒内。
- 权重加载：同样按较慢rank统计，平均2.09秒（1.87–2.33秒），是模型加载的一部分。
- Core日志中的compilation计数平均0.464秒（0.42–0.64秒）。这是已有后端计时口径，不能等同于整个编译调用链或图模式的全部启动成本。
- ACL图捕获日志为7个实例约1秒、1个约2秒，平均约1.125秒；捕获batch 1/2/4，位于6.61秒内。该日志以整数秒输出，精度较粗。
- 当前日志无法把6.61秒进一步精确拆成内存profile、KV分配、编译、算子预热和通信等待，不能将扣除图捕获后的余量全部归因于KV分配。

测量精度：总耗时来自perf_counter，阶段6.61秒来自Core显式耗时。其他三个阶段通过秒级跨进程日志边界推算，单样本边界有约1秒误差，因此它们是估算值。

首个实例18.73秒，前端/激活估算5.96秒，高于其余实例约3.1–3.8秒；slot5为17.95秒，模型加载4.33秒、profile/KV/warmup 7.73秒，也偏高。没有删除这两个较慢样本。

优化判断：优先对6.61秒阶段增加细粒度计时，再检查能否预建/复用KV和图资源；同时定位3.73秒前端激活开销。模型仍每次重载，若要继续降低3.72秒加载成本，需要进一步池化完整已加载engine；这会改变显存占用与模型切换方式。本轮没有实测这些优化收益。
